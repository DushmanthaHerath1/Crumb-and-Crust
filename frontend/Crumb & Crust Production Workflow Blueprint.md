# Crumb & Crust: Production Workflow Blueprint

## Project Brief

"Crumb & Crust" is a digital transformation project for a popular artisanal bakery in Fitzroy, Melbourne. Currently struggling with manual phone and walk-in pre-orders, the bakery needs a reliable digital solution. This project delivers a Mobile-First Digital Pre-order & Kitchen Management System. It features a frictionless Guest Checkout, strict 48-hour fermentation lead-time scheduling, dynamic inventory/capacity management, and a real-time kitchen dashboard for staff to manage order fulfillment securely and efficiently.

## Overview

This document defines a production-oriented workflow for the Crumb & Crust pre-order web application. The recommended architecture is a localized, single-tenant system optimized for a high-volume physical bakery.

The architecture is designed around one core principle: Frontend provides a frictionless user experience, but deterministic backend software layers (FastAPI) control pricing, capacity, validation, and state management. This reduces operational chaos, prevents over-promising on pickup times, and ensures the kitchen operates strictly within its capacity.

## System goals

The system is intended to solve four operational problems at once:

- Capture inbound customer orders without forcing account creation (Guest Checkout).
- Enforce strict artisanal constraints (48-hour fermentation rules, store hours, and daily capacity limits) programmatically.
- Ensure payment security and authoritative order states using Stripe Webhooks.
- Provide a real-time, auditable Kitchen Dashboard with individual staff accountability.

A secondary goal is rapid deployment and cost discipline, utilizing a modern, decoupled stack (React, FastAPI, PostgreSQL) while ensuring the backend runs on paid, always-on infrastructure to prevent cold starts during peak bakery hours.

## Technology Stack

The core technologies are selected for developer velocity, strict type safety, and fast mobile performance:

- **Frontend:** React + Vite (Fast HMR, optimized builds)
- **Styling:** Tailwind CSS (Utility-first, strict design system adherence)
- **State Management:** Zustand (Lightweight global cart state)
- **Backend:** Python + FastAPI (Asynchronous, highly typed API validation via Pydantic)
- **Database:** PostgreSQL (Relational integrity for orders and financial data)
- **Payments:** Stripe (Hosted checkout for PCI compliance)

## Request flow

**1. Storefront browsing & cart assembly**
A customer visits the mobile-optimized web app. They browse the menu and add items to a sticky cart drawer managed globally via Zustand. The frontend prevents adding items that are marked globally as 'sold out'.

**2. Context assembly & scheduling**
Upon clicking checkout, a minimalistic Guest Form collects essential contact details. The frontend calculates the `max_lead_time` from the cart items. It fetches active business hours, blackout dates, and daily capacity caps from the backend. The Date/Time Picker dynamically disables any invalid slots, forcing the customer to select a mathematically valid pickup time.

**3. Backend validation & payment intent**
The frontend sends the order payload to the FastAPI backend. FastAPI strictly re-validates the requested `pickup_time` against product lead times, checks daily capacity limits, and recalculates the total price using database values. If valid, FastAPI creates a pending order in the database and generates a Stripe Checkout Session URL, securely redirecting the customer.

**4. Webhook confirmation (Idempotent)**
After successful payment, Stripe sends a secure Webhook to the FastAPI server. The backend verifies the `Stripe-Signature` header. The webhook handler is idempotent, ensuring that duplicate webhook deliveries do not process the same order twice. The order status in the database is updated from pending to paid, and `paid_at` timestamps are recorded.

**5. Authoritative success rendering**
The customer is redirected back to the app's Success Page. Instead of trusting URL parameters, the frontend makes an authoritative fetch to the backend using the `session_id` to confirm the paid status before displaying the final Order ID and pickup time.

## Schema contract

The schema contract ensures the frontend and backend communicate predictably. All customer orders must conform to a versioned JSON schema validated by Pydantic on the FastAPI layer before any database interaction occurs.

**Core schema fields (Order Payload)**

- `customer_details` (Name, Phone, Email)
- `cart_items` (Array of Product IDs and Quantities)
- `requested_pickup_datetime`
- `idempotency_key` (UUID generated by frontend)

If Pydantic validation fails or business rules (like capacity) are violated, a clear HTTP 400 error is returned, halting the checkout process immediately.

## Database design

The data model supports real-time order tracking, complex scheduling rules, staff accountability, and payment auditing. Security is enforced via strict backend role access and restricting direct browser access to the tables.

**Core tables**

| Table                  | Minimum fields                                                                     | Purpose                                                   |
| ---------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `products`             | `id`, `name`, `price`, `lead_time_hours`, `is_active`                              | Manages menu items and lead-time constraints.             |
| `business_rules`       | `id`, `opening_hours_json`, `blackout_dates`, `daily_order_cap`                    | Controls store availability and overall kitchen capacity. |
| `orders`               | `id`, `customer_json`, `pickup_datetime`, `status`, `stripe_session_id`, `paid_at` | Stores the main order metadata and tracking state.        |
| `order_items`          | `id`, `order_id`, `product_id`, `quantity`, `subtotal`                             | Normalized line items for each order.                     |
| `admin_users`          | `id`, `email`, `role`, `created_at`                                                | Stores individual staff accounts (Owner/Staff) for Auth.  |
| `order_status_history` | `id`, `order_id`, `changed_by_user_id`, `old_status`, `new_status`                 | Audit log for tracking who moved an order state.          |

## Order states

The system utilizes a strict state machine to keep kitchen operations auditable and prevent lost orders.

- `pending`: Order initiated, awaiting Stripe webhook confirmation. (Never shown to kitchen).
- `paid`: Payment verified, order is active and visible on the Kitchen Dashboard.
- `ready_for_pickup`: Staff physically prepared the items and updated the dashboard.
- `completed`: Customer collected the order.
- `failed` / `refunded`: Payment failed or was manually reversed by the owner.

Every transition from `paid` onwards is logged in `order_status_history` tied to the specific staff member's ID.

## Infrastructure & Deployment Stack

**Stage 1: Local Development & Staging (Zero Cost)**
Use local environments for rapid iteration without triggering cloud costs or strict expiry limits.

- **Frontend:** Vite/React runs locally (`localhost:5173`).
- **Backend:** FastAPI runs locally (`localhost:8000`).
- **Database:** Connected to a Supabase test project (Sufficient for active development).
- **Payments:** Strictly processed using Stripe Test Mode and local CLI Webhook forwarding.
- **Staging:** Frontend deployed to Vercel (Hobby). Backend deployed to Render (Free Tier) — _Note: Client is informed of 50-second cold starts during staging._

**Stage 2: Production Launch (High Reliability)**
Production infrastructure shifts to paid, always-on tiers to guarantee transaction safety and prevent auto-pause interruptions.

- **Frontend Hosting:** Deploy to Vercel Pro (or Hobby if traffic permits). Configured to the Singapore (sin1) edge region to guarantee minimal latency for development and maintenance from Sri Lanka, while maintaining fast load times for the Australian customer base.
- **Backend Hosting:** Deploy the FastAPI backend to Render on a paid tier (Starter plan - ~$7/month) to ensure continuous uptime and zero cold-start latency for webhook processing.
- **Database Hosting:** Render Managed Postgres Basic (~$6/month). This ensures permanent uptime, bypassing Render's 30-day free database deletion and Supabase's 7-day pause policies. Configure database with strict policies, ensuring only authenticated staff can read orders, and only the backend service role can write them.
- **Payments:** Stripe Live Mode.
- **Total Operating Cost:** ~$13/month.

## Operational guardrails

A production-safe bakery system relies on strict non-functional safeguards:

- **No Client-Side Price Trust:** The backend independently calculates the final Stripe payload.
- **Strict Webhook Verification:** `Stripe-Signature` must be validated to prevent spoofed payments.
- **Individual Accountability:** Shared passwords are prohibited; individual staff accounts ensure a clear audit trail.
- **Capacity Enforcement:** The backend will reject an order if the `daily_order_cap` is exceeded precisely at the moment of checkout.

## Recommended v1 scope

The most realistic first version for Crumb & Crust should include:

- Mobile-first frontend with hybrid category grid.
- Guest Checkout flow.
- Backend-enforced 48h lead time, business hours, and daily cap logic.
- Stripe Hosted Checkout with secure Webhooks.
- Kitchen Dashboard with individual Staff/Owner roles.
- Order status audit trailing.

The following should be deferred to future phases to keep the MVP lean:

- Customer accounts and loyalty programs.
- Per-15-minute slot capacity logic (daily caps are sufficient for V1).
- Automated SMS notifications (Email receipts via Stripe are sufficient).
